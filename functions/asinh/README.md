## Algorithm

With a = |x| and asinh(−x) = −asinh(x) (the sign is XORed back at the end):

- a < 0.0221 (`kSmallX`): asinh(a) = a + a·x²·(C1 + C2·x² + C3·x⁴).
- otherwise asinh(a) = log(Xin) with Xin = a + √(1 + x²), evaluated as a double-double Xin0 + Xin_low:
  - Y = 1 + x² = Yh + Yl exactly (Yl from max/min(x², 1) and the FMA error of x²);
  - R0 = `vrsqrt14pd`(Yh), a 14-bit approximation of 1/√Yh; Sh = Yh·R0, Sl = (Yh·R0)_low + R0·Yl;
    Eh = 1 − Sh·R0 − Sl·R0 is the relative error of R0²·Y (~2⁻¹⁴), and
    √Y = (Sh + Sl)/√(1 − Eh) ≈ Sh + Sl + Sh·Eh·(1/2 + 3/8·Eh + 5/16·Eh² + 35/128·Eh³);
  - Xin0 = (Sh + a) + correction, Xin_low collects the rounding errors of both additions;
  - a ≥ 2⁵¹¹ (`kLargeX`, where x² overflows): Xin = a/8, Xin_low = 0, and 4·ln2 is added (log(2a) = log(a/8) + 4 ln2).
- log(Xin): Rcp = `vrcp14pd`(Xin0), rounded to 1+4 mantissa bits by an integer add of 2⁴⁷ and a mask;
  R = Rcp·Xin0 − 1 + Rcp·Xin_low (exact first part, |R| ≲ 2⁻⁵); K = `vgetexppd`(Rcp);
  log(Xin) = −K·ln2 + Th[k] + Tl[k] + R + R²·P(R), with 16-entry tables −log(1 + k/16) (high and low
  parts, `vpermt2pd` with the 4 mantissa bits of Rcp as index) and P of degree 8. The terms are summed as
  a double-double (high: −K·L2H + Th + (Rcp·Xin0 − 1), low: −K·L2L + Tl + Rcp·Xin_low + its rounding error + R²·P).
- Lanes with |x| > DBL_MAX (±inf) or NaN call the scalar routine, which returns x (±inf) or x·x (quiet NaN).

Both paths are computed for all lanes and selected with masks; there are no branches except the callout.

## The C translation

`svml/svml_asinh_d_ha.c` translates the assembly into C with AVX-512 intrinsics, instruction for instruction:
same constants (bit-exact hex-float literals generated from the data section), operation order and
rounding (`{rn-sae}`/`{sae}` on every instruction, `_CMP_NLT_UQ`/`_CMP_NLE_UQ` predicates as in the assembly).
Its results are bit-identical to `__svml_asinh8_ha` (`test_asinh8`).

- `svml_asinh8_ha(__m512d)`: the vector routine (needs AVX-512F at run time; only this function is compiled
  for AVX-512). `svml_asinh_ha_array(x, y, n)`: loop with a masked tail.
- `svml_dasinh_ha_cout_rare()`: the scalar routine, plain C.
- Differences that do not affect results: the bitwise operations use AVX-512F integer forms (`vpandq`,
  `vpxorq`) instead of `vandpd`/`vxorpd` (AVX-512DQ); two empty `asm` barriers keep GCC from merging the
  sign-bit operations into `vpternlogq`, so that `make asinh-insns` sees the same instruction mix.

## Highway version (`hwy/`)

`hwy/hwy_asinh.cc` is the same algorithm written with [Google Highway](https://github.com/google/highway)
(1.4.0 from conda-forge), with run-time dispatch:

- targets with true FMA (`HWY_NATIVE_FMA`: AVX2, AVX3*, NEON, SVE/SVE2, ...): every operation of the
  translation in the same order, with the AVX-512-only instructions emulated exactly (below), so the results
  are **bit-identical to Intel's `__svml_asinh8_ha`** on all of them;
- targets without FMA (SSE2/SSSE3/SSE4): `std::asinh` (the double-double steps need a fused multiply-add).

Lanes with |x| > DBL_MAX or NaN use the C callout. Two independent vectors are evaluated per loop iteration
and, with GCC, the object is compiled with `-fschedule-insns -fsched-pressure` so that they are interleaved:
one evaluation is a long dependency chain and the loop is otherwise latency-bound (1.5x slower on AVX2).

### Emulation of the AVX-512 instructions (`hwy/avx512_emul-inl.h`)

| instruction | emulation |
|---|---|
| `vrsqrt14pd` | exact, see below |
| `vrcp14pd` | exact, see below |
| `vgetexppd {sae}` (of Rcp: positive, normal) | exponent field ORed into the mantissa of 2⁵², minus 2⁵² + 1023 (exact; no int64→double conversion, which AVX2 lacks) |
| `vpermt2pd`/`vpermi2pd` (16-entry tables) | `TwoTablesLookupLanes` (one `vpermt2pd` on AVX-512); on 4-lane AVX2 two of them and a select on index bit 3; on 2-lane NEON/SVE-128 four and three selects; the whole table in one `TableLookupLanes` for ≥ 16 lanes; `GatherIndex` only for single lanes and SVE lengths that are not a power of two (e.g. 384 bits). No gathers on x86. |
| `vmaxpd`/`vminpd {sae}` | `Max`/`Min` (differ only for NaN, which goes to the callout) |
| `vcmppd` NLT_UQ / NLE_UQ | `Not(Lt(...))` / `Le` (the unordered "true" for NaN is kept where it matters) |
| masked `vmulpd`/`vsubpd`/`vaddpd`, masked zeroing | the unmasked operation and `IfThenElse`/`IfThenZeroElse` |
| `vpaddq`/`vpsrlq`/`vandpd`/`vxorpd` | integer and bitwise operations on `BitCast` vectors |
| `{rn-sae}` | default rounding; the suppressed exception flags are not emulated (the Highway version may raise inexact/invalid flags that Intel's code does not; results are unaffected) |

**VRCP14PD and VRSQRT14PD.** The SDM only bounds their relative error (2⁻¹⁴), so they are often taken to be
implementation-defined. But Intel publishes a bit-exact reference ("Reference Implementations for IA
Approximation Instructions VRCP14, VRSQRT14, VRCP28, VRSQRT28, and VEXP2", `RECIP14.c`, BSD-3-Clause),
which Intel SDE follows; `tests/test_approx14` confirms it against the instructions (under SDE here) for every
mantissa prefix that matters. For a mantissa in [1, 2) (rcp14) or [1, 4) (rsqrt14) the reference evaluates a
linear function on one of 64 segments with integer coefficients,
r = a[i] − 256·b[i]·(xt − y[i]), where y[i] is the centre of segment i and xt is x truncated to 17 (rsqrt:
16) significant bits, and truncates r to 17 bits (everything is exact in double precision). The results
depend on x only through its exponent and top 16 (rcp14) or 15 (rsqrt14, plus the exponent parity) mantissa
bits.

Does SVML make the final result independent of these bits? Not entirely. Rcp is rounded to 5 significant
bits, but rcp14 lies within 2⁻¹⁴ of a rounding midpoint for a fraction of inputs, and a different Rcp gives a
different (equally valid) reduction and table entry; R0 determines the rounding errors of Sh, Sl and Eh and
the truncation error of the series in Eh (~2⁻⁵⁶ relative), which reach the last bit of Xin_low. Replacing rcp14/rsqrt14 in the C translation by 1/x or 1/√x (correctly rounded, then truncated
to 17 bits, i.e. another approximation of the same quality) changes 84 of 2,005,648 asinh results with
rsqrt14 (3 for acosh), and 0 for asinh and acosh / 1 for atanh with rcp14 (measured under SDE). Only an exact
emulation gives bit-identity, so the Highway version emulates both instructions exactly:

- the 64-entry coefficient tables would need gathers, so the coefficients are computed:
  b = 2·⌊512/y²⌋ + 1 and d = 2·⌊K/y^1.5⌋ + 1 (K = 512 on [1, 2), 1024 on [2, 4)) hold for every segment;
  a = ⌊2¹⁸/y⌋ + ra[i] and c = ⌊2¹⁹/√y + α·y^−2.5 − 2⌋ + rc[i] (α = 20.5 / 46.5) with corrections
  ra, rc ∈ 0..15 stored as 4-bit fields in four 64-bit words (selected with two `IfThenElse` on the index
  bits, extracted with a variable shift). One division (rcp14), a square root and a division (rsqrt14).
  `tools/gen_approx14.py` simulates the vector code's double operations (FMAs rounded once via exact
  rationals) to derive the corrections and checks the b/d formulas;
- y[i] and xt are built from the mantissa bits; xt − y is exact; r = NegMulAdd(256·b, xt − y, a) is exact
  (exactly representable, so the fused operation does not round); the truncation, the exponent
  (1023 − e for rcp14, −⌊(e − 1023)/2⌋ for rsqrt14) and the special cases (powers of two / of four, ±0, +inf,
  NaN) are integer operations.

Domain of the emulation: rcp14 for positive normal x with a normal reciprocal; rsqrt14 for ±0, +inf, NaN
and positive normal x. That covers every lane whose result is used (Xin ≥ 1 or ≥ 2⁻⁵³ in atanh, Y ≥ 0);
callout lanes may compute garbage that is then replaced.

The cost: on AVX2 (i5-9500) the emulations take about 3.5 of the 8 ns/value (with 1/√x and 1/x instead, the
same code runs in 4.5 ns/value, but is not bit-identical; see Performance.md).

### Verification

- under Intel SDE (`make asinh-avx512-test`): the AVX3, AVX3_DL, AVX3_SPR and AVX2 targets give results
  bit-identical to the C translation (which is bit-identical to the assembly), and their hashes equal the
  translation's (`C-AVX512 svml` line of `--hash`);
- `make asinh-xcheck` (pixi `cross` environment): AArch64 NEON, SVE at 128/256/384/512/2048 bits and SVE2
  under QEMU produce the same bits as x86-64 AVX2;
- in CI, `make hashes` compares the AVX2 and NEON/SVE hashes with the SDE run of the translation.

Inputs (`tests/inputs.h`): ±0, ±inf, NaNs, denormals, ±DBL_MAX; ±50 ulps around every threshold (0.0221,
2⁵¹¹, DBL_MAX, the overflow and underflow of x², 2⁻²⁶ where 1 + x² rounds to 1, ...); inputs for which Xin
is at or next to the rounding midpoints of the 5-bit reciprocal and the table boundaries; random values
uniform in [−0.05, 0.05], [−2, 2], [−1000, 1000], log-uniform over the whole range, and random bit patterns.
All are built with IEEE operations only (no libm), so they are identical on every architecture.
