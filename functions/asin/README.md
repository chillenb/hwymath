## Algorithm

With a = |x| (the sign of x is restored with a final xor), Y = 0.5 − 0.5a and R = min(a², Y):

- a < 0.5: asin(a) = a + a·R·P(R), P of degree 11 (asin(s) = s + s³P(s²)), Horner/Estrin mix in R, R², R⁴;
- a ≥ 0.5: asin(a) = π/2 − 2 asin(√Y) = π/2 − s − s·R·P(R) with s = 2√Y (R = s²/4, the same polynomial).
  2√Y is computed as a double-double Sh − Sl without a square root instruction: r = `vrsqrt14pd`(Y)
  (relative error < 2⁻¹⁴, forced to 0 for Y < 2⁻²⁵⁵, i.e. a = 1), Sh = RN(2Y·r), its exact rounding error
  Sh_err = 2Y·r − Sh (FMA), e = RN(2Y·r² − 2), and Sl = Sh·e·(c₀ + c₁e + c₂e² + c₃e³) − Sh_err (the series
  of (1 + e/2)^(−1/2) − 1). π/2 − Sh is formed with its rounding error (Fast2Sum-like), and the low parts
  π/2_lo + Sl − err enter the polynomial term before the final addition.

Lanes with |x| > 1 (including ±inf) are recomputed by the scalar routine
`__svml_dasin_ha_cout_rare_internal`, which returns NaN with the invalid exception and code 1. NaN inputs
stay on the vector path, whose result is the quieted input NaN. The scalar routine is a complete scalar
asin (inf/NaN, |x| > 1, x + x² for tiny x, a double-double series for |x| < 0.5 with a 2²⁷+1 splitting,
and a table-driven double-double square root for |x| ≥ 0.5); only its |x| > 1 / inf branch is reached
from the vector code.

## The C translation

`svml/svml_asin_d_ha.c` keeps the algorithm, the constants (bit-exact hex-float literals), the operation
order and every instruction's rounding mode, so its results are bit-identical to Intel's (`test_asin8`).

- `svml_asin8_ha(__m512d)`: the vector routine (AVX-512F at run time); `svml_asin_ha_array(x, y, n)`.
- `svml_asin8_ha_portable(__m512d)`: the same with `vrsqrt14pd` replaced by the Highway version's
  portable approximation (below), keeping NaN payloads like the instruction; the reference for the
  Highway targets.
- `svml_dasin_ha_cout_rare(&x, &r)`: the scalar callout as portable C, generated by `tools/asm2c.py`.

### The mechanical callout translation (`tools/asm2c.py`)

The four inverse-trigonometric callouts are about 260 to 730 scalar SSE2 instructions each (asin's: about
440), so they are not rewritten by hand: `asm2c.py` turns every instruction into one C statement on a
small machine model (`svml/asm_model.h`, each statement annotated with the instruction): xmm registers are
doubles, general-purpose registers are `uint64_t` with x86 sub-register semantics, memory is real memory
(a stack array for the red zone, the caller's pointers, the data tables as `uint64_t` arrays with the
assembly's bits), and the condition flags are the operands of the last flag-setting instruction, evaluated
by the jumps (`comisd` with signaling C comparisons, `ucomisd` with `isgreater` etc., so the same FP
exceptions are raised). The tables are writable and zeroing reads a volatile zero, so that the compiler
cannot constant-fold operations whose exceptions must be raised at run time. Elsewhere than on x86, the
arithmetic helpers also produce x86's NaN results (first NaN operand, negative default NaN), so the
callouts give the same bits on AArch64. The result is portable C (little-endian assumed) that GCC/Clang
compile into ordinary register code; `test_rare` checks results, return codes and FP flags against the
assembly bit for bit. The algorithm summary above is from reading the assembly; the generated code itself
is not meant to be read.

Differences of the vector translation from the assembly that do not affect results: the bitwise
operations use the integer forms (`vpandq`/`vpxorq`, AVX-512F) instead of `vandpd`/`vxorpd` (AVX-512DQ);
empty `asm` barriers keep GCC from rewriting `x ^ |x|` and the final xor as `and`/`vpternlogq`, so that
`make asin-insns` compares equal instruction mixes; register allocation and FMA forms (132/213/231) are
the compiler's.

## Highway version (`hwy/`)

`hwy/hwy_asin.cc` ports the same algorithm with [Google Highway](https://github.com/google/highway) 1.4 and
run-time dispatch:

| AVX-512 feature | emulation |
|---|---|
| `{rn-sae}` arithmetic and FMAs (`vfmadd`, `vfmsub`, `vfnmadd`) | `Mul`/`Add`/`Sub`/`MulAdd`/`MulSub`/`NegMulAdd`: the same IEEE operations in round-to-nearest |
| `vminpd {sae}` | `Min` (NaN lanes are replaced at the end, so its NaN semantics do not matter) |
| `vcmppd` (LT_OQ, NLT_UQ) | `Lt`, `Not(Lt)` |
| masked `vsubpd`/`vxorpd`, `vblendmpd` | `IfThenElse`, `IfThenElseZero`, `IfThenZeroElse` |
| NaN propagation | NaN lanes are set to `x + x` (the quieted input, as the SVML code returns) |
| `vrsqrt14pd` | **not reproducible**: see below |

`vrsqrt14pd`'s result bits are implementation-defined. Under Intel SDE they are a function of the top 15
mantissa bits and the exponent parity of the input and have at most 16 significant bits; reproducing
them would need a table of 2¹⁶ entries (gathers, which this project avoids; Intel does not document the
function). The final result depends on them for a ≥ 0.5: Sh = RN(2Y·r) and the split of 2√Y into Sh − Sl
change with r, and with them the rounding errors of π/2 − Sh and of the final sum. (For a < 0.5 the
result does not depend on r: the sqrt branch is masked out.) The Highway version therefore uses
**trunc16(RN(1/RN(√Y)))** (two correctly rounded IEEE operations, mantissa truncated to 16 bits: the same
format as Intel's, relative error < 2⁻¹⁵·⁹ instead of 2⁻¹⁴) on every FMA target. Consequences:

- the results are bit-identical on every FMA target and machine (only IEEE operations: x86-64 AVX2 and
  AVX-512, AArch64 NEON/SVE/SVE2 checked under QEMU, RVV by construction), and equal to
  `svml_asin8_ha_portable`;
- they differ from Intel's in 620 of the 2,004,655 test inputs (0.031 %, all with |x| ≥ 0.5); max error
  and not-correctly-rounded rate stay those of Intel's code (0.829 vs 0.829 ulp, 6.10 vs 6.08 % on these
  inputs);
- `hwy_asin_native_array` uses `vrsqrt14pd` itself on AVX-512 targets (`ApproximateReciprocalSqrt`): it is
  bit-identical to Intel's code on the same CPU (verified under SDE), which also proves that all other
  operations are emulated exactly. On other targets it is the same as `hwy_asin_array`.

Targets without FMA (SSE2/SSSE3/SSE4) use `std::asin`. Lanes with |x| > 1 use the C callout (out of line,
`cold`). Despite the division and square root, the AVX2 version is as fast as Intel's libsvml AVX2 code on
the Core i5-9500 (2.3 ns/value).

## Tests (`make asin-test`, `make asin-avx512-test`)

| test | compares with | result |
|---|---|---|
| `test_rare` | Intel's scalar `__svml_dasin_ha_cout_rare_internal`: results, return codes, FP exception flags | 20,004,655 inputs, 0 mismatches |
| `test_asin8` | Intel's `__svml_asin8_ha`, all 8 lanes bit-exact | 2,004,656 inputs, 0 mismatches (Intel SDE `-spr`); skipped (77) without AVX-512 |
| `hwy_test` | every Highway target: error bound (max ≤ 0.9 ulp, none > 1 ulp), special inputs (NaN, ±inf, \|x\| > 1, ±0), identical results on all FMA targets; with AVX-512: bit-identity of every FMA target with `svml_asin8_ha_portable` and of the native variant with `svml_asin8_ha` | all checks pass (AVX3_SPR, AVX3_DL, AVX3, AVX2 under SDE; AVX2 natively) |
| `make asin-insns` | arithmetic instruction mix of the compiled vector path vs the assembly | identical |
| `make asin-xcheck` (`pixi run -e cross`) | Highway NEON, SVE and SVE2 under QEMU (SVE at 128, 256, 512, 1024 and 2048 bits, i.e. 2 to 32 lanes) vs x86-64 AVX2: inputs and results bit for bit (`functions/asin/tools/xcheck_invtrig.sh`) | identical on all 11 AArch64 configurations (200,000 random inputs plus the edge cases) |

Inputs (`tests/inputs.h`): special values (±0, ±inf, NaNs with payloads, denormals, ±1, ±DBL_MAX, ...),
±50 ulps around every threshold of the vector code and the callout (0.5, 1, 2⁻⁵³, 2⁻¹⁰²², ...),
arguments approaching ±1 (1 − 2⁻ᵏ), and random values (uniform in [−1, 1] and [−1.25, 1.25], log-uniform
magnitudes in [2⁻⁶⁰, 1], arbitrary bit patterns). `make asin-hashes` writes the result hashes (`port` per
Highway target, `native` per AVX-512 target, and with AVX-512 the C translation's `svml-c intel` and
`svml-c port`) for the cross-machine check: every `port` hash must equal `svml-c port`.
